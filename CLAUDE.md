## 1. The product

The completed upstream spec is the authority, not this list (section 2).

## 2. Standing law - upstream and parity

1. **The owner asked for the full functionality of FastMediaSorter's Filler**, not a partial or redesigned substitute. FastMediaSorter S4521 (`PLAN/S4521_local-storage-filler.md` in the upstream checkout) is the source of behaviour, and its checkout is never modified from here.
2. **Re-inventory before any parity claim.** The bootstrap snapshot is not a baseline. Every port ticket (S0003 to S0006, and the follow-on ports of later upstream additions such as S0008 and S0009, which cite their FastMediaSorter ticket) first reads S4521's actual status, its final spec, code, resources and tests. While the upstream is unfinished, upstream-dependent work is parked behind a concrete external blocker; parity is claimed only against the completed source.
3. **Port, do not rewrite.** A behaviour that can be ported with its tests is ported; a deliberate difference is recorded next to the code it concerns. The form of the parity inventory is decided in S0003's plan pass; StreamsPlayer_mob and Tourist_mob keep a committed port ledger with a SHA-256 drift check, a model to reuse.
4. **No device claim without a device.** A real-device scenario that has not happened stays an open manual check in its ticket (S0006), never a pass.

- **Release package plan** - six decisions, recorded once:
  1. Files: `PLAN/RELEASE_QUEUE.md` (work remaining), `PLAN/RELEASE_READY.md` (ready), `PLAN/RELEASE_QUEUE_DONE.md` (shipped history, newest first).

  3. Ready set: `Implemented`, `Verified`, `BlockNeedUserTest`. Work remaining: `Draft`, `Approved`, `Tactical`, `In Progress`, `Partial`, `Broken`, `BlockByOtherTask`, `BlockQuestions`, `BlockExternal`. `Archived` leaves the plan.
  4. Package number: the `current-next-release:` marker in `PLAN/RELEASE_QUEUE.md`, starting at 1, advanced by `-Ship`. Not tied to a branch. `--` is the not-scheduled bucket.
  5. Operator commands (all through `tools/harness.ps1 spec_catalog/release-queue`): `-List`, `-List -Ready`, `-Validate`, `-Reconcile`, `-SetCurrent N`, `-Ship -Release N [-Version X] -DryRun`. Package headings and line order are the owner's; no script reorders them.

## 5a. Build architecture - what spans several files

- **The app source is a skeleton.** `phone/src/main` holds one `MainActivity` and its layout; the engine, storage adapter and user flow do not exist yet and arrive only through S0003 to S0005, whose chain waits on the upstream (S0005 -> S0004 -> S0003, `BlockExternal` on FastMediaSorter S4521 being Verified). Read the live state with `tools/harness.ps1 spec_catalog/release-queue -List`, not from this file; do not write Filler logic ahead of its port ticket.
- **The version is stamped, never typed.** `buildSrc/src/main/kotlin/com/sza/filler/buildlogic/VersionStamp.kt` renders one `yyMMddHHmm` instant into both `versionName` (`Y.YM.MDDH.Hmm`) and `versionCode` (`yyMMddHH * 10 + minute/10`); `phone/build.gradle.kts` calls it once at configuration time from the clock, or from a `-Pfiller.versionName/-Pfiller.versionCode` pair (both or neither, validated to describe one instant). That is why `org.gradle.configuration-cache=false` in `gradle.properties`: a cached configuration would replay a stale instant. Do not turn it on and do not check in a version literal. `buildSrc` is also where the unit tests of this logic live (`buildSrc/src/test`); the app module has no tests yet.
- **The release guard lives in `phone/build.gradle.kts`.** A `gradle.taskGraph.whenReady` hook refuses `assembleRelease`, `bundleRelease` and `packageRelease` while `provisionalApplicationId` ends in `.provisional`. Choosing the published id (S0007) is what lifts it; never work around it.
- **One dependency catalog, two consumers.** `gradle/libs.versions.toml` is read by the root build and, through `versionCatalogs { from(files("../gradle/libs.versions.toml")) }`, by `buildSrc/settings.gradle.kts`. Both settings files use `FAIL_ON_PROJECT_REPOS`, so a repository or a version declared inside a module is an error. The Kotlin plugin is not declared anywhere: AGP 9 carries its own Kotlin, and the Kotlin version follows `agp`.
- **The harness is configured by `.sza-profile.json` only** (module `phone`, lock domains `Build.Main`, `Code.Main`, `Code.Scripts` with the path rules that map files to them). A new top-level directory that holds code needs a path rule there, or the lease locks do not cover it.

## 6. Verification between releases

Between releases run only checks measured at 5 seconds or less and a direct inspection of the change; defer the full build and slower or unmeasured tests to the release (TESTING_AND_QA section 2). Record each skipped rung in the ticket audit as `RELEASE` with the exact release command; report "not built, not tested until the release".

- **Fast tier:** `pwsh -NoProfile -File tools/harness.ps1 spec_catalog/validate` (0.8 s, 2026-11-10) and `pwsh -NoProfile -File tools/harness.ps1 spec_catalog/release-queue -Validate` (0.8 s, 2026-11-10); the canon compliance gate `tools/check-compliance.ps1` run from the installed plugin root (1.2 s, 2026-11-10); and `.\gradlew.bat -p buildSrc test`, the fixed-instant vectors of the version stamp (9 tests, 1.3 s to 1.5 s forced with `cleanTest test` and 2.5 s to 3.3 s after a source edit, on a warm daemon, 2026-11-10). One test: `.\gradlew.bat -p buildSrc cleanTest test --tests 'com.sza.filler.buildlogic.VersionStampTest.noPinIsNoPair'` (quote the filter in PowerShell; 1.4 s to 1.5 s on a warm daemon, 2026-11-13, but 6.7 s for the first run after an idle spell). The first run with no live daemon takes 29.9 s: check `.\gradlew.bat --status` and, with no idle daemon, count the run as release tier. Site (2026-11-13): `pwsh -NoProfile -File tools/site/check-site.ps1` (0.66 s; one h1, canonical, og:url and hreflang per page, relative links, sitemap and robots, the kit hash, no three dots; run after editing `site/` and before any claim about the site) and `pwsh -NoProfile -File tools/store/render-store-assets.ps1` (0.41 s; after changing the launcher glyph).
- **Release tier:** `.\gradlew.bat :phone:assembleDebug` - 61.5 s for the first build, 45.1 s in a clean copy of the tree, 7.4 s warm with `--rerun-tasks` (2026-11-10). It is the only packaging task: `assembleRelease`, `bundleRelease` and `packageRelease` are refused while the application id is provisional. Skipped rungs are reported as "not built, not tested until the release".
- **Running Gradle** (S0002): from the repository root with `.\gradlew.bat`; a `-P` argument is quoted in PowerShell, or the shell splits it at the dot. It needs a JDK 17, 21 or 25 (`org.gradle.java.home` in the user's `%USERPROFILE%\.gradle\gradle.properties`, never in the repository) and the Android SDK location, in the gitignored `local.properties` (`sdk.dir=..`) or in `ANDROID_HOME`. A release orchestrator pins the version with `'-Pfiller.versionName=..' '-Pfiller.versionCode=..'`, both or neither. No pass has installed the app on a device (section 2.4).
